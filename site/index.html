01 项目从哪里开始

任务还在继续。
上下文已经变了。

Agent 执行一段长任务时，数据库可能换了表结构，工具的权限可能被收回，用户也可能修改了先前的要求。

如果只把消息不断追加给模型，旧信息与新约束会混在一起。Reactive Context 把这些变化变成可以管理、核验和追溯的状态。

01 / 时效

外部来源更新了，
模型还在读旧版本。

把 Skill、工具目录和 Schema 作为独立 Part，在每次请求边界核验来源版本，刷新受影响的依赖。

02 / 延续

历史越来越长，
有效约束却越来越难找。

保留原始归档，区分近期历史、长期 Fact 与当前工作状态；需要时，通过授权的检索路径恢复证据。

03 / 可解释

回答出了问题，
却不知道这一轮看到了什么。

每次编译保留来源、版本、入选原因与省略诊断，让模型实际输入有据可查。

定位：接入已有 Agent Runtime 的 Python 库。任务规划、工具执行与模型推理由宿主框架负责。

异步读取晚到，怎么避免旧值覆盖新值？

每个 Part 的解析受单飞控制。解析前记录 generation，完成时重新检查；期间依赖发生变化，就丢弃过期结果或按策略重试。声明式来源还会在最终封存前核验版本。

一致性依赖来源版本的可信度；多个外部系统并不天然拥有同一时刻的全局原子快照。

文件监听漏了通知，还能发现变化吗？

通知负责及时标记 dirty，请求边界的 revision 核验负责确认当前版本。无版本能力的来源标记为 best_effort，严格模式拒绝静默降级。

为什么要编译成快照，而不是直接拼消息？

Part 通过统一中间表示交付内容，Compiler 集中执行权限、预算和顺序规则。必需内容无法纳入时明确失败，可选内容被省略时保留诊断。已有快照不会随之后的状态修改。

04 记忆与当前工作
有些信息，值得留下。

记得过去。
专注当下。

历史、事实、目标和状态，
不必挤在同一段摘要里。

01

原始历史 History

记录实际发生的消息、工具请求与结果。完整归档用于审计和恢复，本次模型输入使用独立投影，并保护当前工具协议链。

02

长期事实 Fact

通过宿主接入的写入流程，按 schema、来源和版本检查入库。保存不等于自动进入模型，读取与激活仍受权限约束。

03

工作目标 Objective

表达当前要完成什么，以及下一步方向。独立于历史摘要，由宿主或受控工具在适当时机更新。

04

工作状态 WorkState

保存当前方案与有效约束。用字段级 patch 修改，未涉及的字段默认保留；删除、清空与替换分别检查许可。

从候选到提交

提出修改，
不等于已经生效。

  1. 提案补丁与来源
  2. 校验权限与业务条件
  3. 待提交ready ≠ committed
  4. 原子提交重检版本并写入增量

缺证据的候选保持 pending，验证失败的候选不会覆盖当前状态。要求改变后，旧许可撤销；正式提交时再次校验，避免使用过期的检查结论。

05 设计手记

工程的分量，
藏在取舍里。

这个项目的重点是把输入构造变成可检查的工程过程。下面这些边界，与功能本身同样重要。

01

复用 Agent 循环

通过 Pydantic AI 的请求边界接入，保留宿主的工具执行、流式输出、重试和会话恢复。

取舍：框架升级需要重新验证适配契约；当前未交付真实 DSH 生产插件。
02

权限不能靠 Prompt

Skill 的指令角色需要宿主明确授权。Fact、网页和检索结果保持数据身份，不能自行升级为 system 指令。

取舍：scope 标签不等于 ACL；业务工具副作用与执行授权仍由宿主负责。
03

激活与常驻分离

Active Set 保存资源引用与策略。SQLite 管元数据，大载荷放文件系统，热层按字节限制缓存。

取舍：聚焦嵌入式部署，当前不承诺跨主机共享与分布式事务。
04

两层缓存，分别观察

库内缓存复用 Part 解析与计算；稳定排序帮助减少模型请求前缀的无意义变化。

取舍：应用缓存复用不等于服务端缓存命中，也不自动意味着总费用下降。
05

小历史，需要恢复路径

近期窗口控制常驻输入，原始历史保留检索和读取入口。摘要作为可选机制，不承担当前状态的全部职责。

取舍：模型仍可能不查历史、查错或误用结果；通用库不保证自动恢复成功。

07 从一段 Python 开始

声明状态。
让依赖自己连接。

state 保存本地状态，computed 表达同步派生计算，异步 part 在编译或显式解析时读取外部来源。

声明式入口与原有工厂 API 汇入同一个 Registry 和 Compiler。实例间隔离，不在普通属性访问时隐式执行异步 IO。
